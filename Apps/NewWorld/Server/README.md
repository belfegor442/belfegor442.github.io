# New World legacy .NET server reference

**This service is no longer used by the published New World web application.** The active browser client follows the BREW model: the player who creates a room runs the authoritative game state and rules in their browser. Other players connect through a public MQTT relay; the relay transports messages but does not simulate or persist the world. Do not deploy this .NET service or provision PostgreSQL for normal New World multiplayer.

The .NET 8 project and its tests are retained as a reference for domain rules and validation while those rules are migrated into the browser-hosted runtime. Its former API, WebSocket, and PostgreSQL deployment instructions below are historical and do not describe the active multiplayer architecture. The persisted world record includes session metadata, a Gregorian world date, stable State IDs, government memberships, State-specific currency identities, shared treasuries, and a financial transaction ledger. Legacy player treasuries are migrated into their assigned State with an opening-balance record.

## Run locally

Install Docker Compose, then run in PowerShell from `Apps\NewWorld`:

```powershell
$env:POSTGRES_PASSWORD = "choose-a-long-random-password"
docker compose up --build
```

Open the New World page, select **PLAYERS**, enter `http://localhost:5000` as the server URL, and test the connection. Create a world and share its invitation code. A lobby admits up to 20 human players, and multiple players can share a State government. The existing lobby assignment and start controls remain technical setup for this MVP; who approves admission is still a pending design decision, not an established political rule. New games start on 1 January 1500. Once started, connected players can vote to pause or resume; the owner-confirmed rule is a strict majority of currently connected players. Pending votes reset whenever the connected player set changes. New players cannot join after a world has started in this MVP.

The browser's sample figures are preview-only. There is no single-player simulation or local save; play requires a multiplayer server. The initial Beleland scenario contains 16 States; State and currency identifiers derive from stable scenario keys, so a label change does not change entity identity.

The State treasury and monthly balance are shared by all members. Each member's construction plots remain separate for now, while their building income and upkeep contribute to their selected government's finances.

The economic core executes explicitly configured goods and production recipes on each authoritative world day. Facilities consume available inventory, reduce batch volume when inputs are scarce or configured output storage is nearly full, and emit persistent production events; company inventories, storage limits, and facility progress are exposed in snapshots. Unconfigured storage limits remain uncapped; saved capacities must be positive and cannot be lower than existing stock.

Configured State/good markets now clear daily against company inventories. Supply is offered from local firms and, where an enabled bilateral trade route exists, from exporting-State firms up to the route's daily capacity. Route capacity and market sales are allocated proportionally across eligible inventories, with stable IDs breaking indivisible-unit remainders. The demand used for prices and clearing is configured daily demand plus demand derived from population-group needs. Each market's target price is `clamp(basePrice * totalDailyDemand / availableSupply, minimumPrice, maximumPrice)`; zero demand targets the floor, and positive demand with no supply targets the ceiling. `PriceSmoothingPercent` moves the current price toward that target each day using integer arithmetic. Purchases are capped by demand, available stock, and `dailyConsumerBudget / currentPrice`. Sellers' inventory is decremented and sale proceeds are credited to a company cash account in the buying market's currency; State treasuries are not used as company cash. Settlements, prices, sales, unmet demand, and company cash transactions are persisted and included in snapshots. Companies can hold balances in multiple currencies, so inter-State sales do not silently convert or sum currencies.

Routes may instead name an exporter and importer company and specify a contracted daily quantity and unit price. Different company pairs can hold parallel contracts for the same good and State pair; each pair has one contract per good. These deliveries settle directly between the two company inventories and cash ledgers in the importing State's currency, capped by route capacity, exporter stock, importer storage, and buyer funds. Imported goods cannot be resold through another contract or a market on the same day. Route execution is staged with the rest of the daily clearing, so a failed payment or overflow does not partially apply the day's trades.

The host can configure or replace goods, recipes, NPC companies, markets, bilateral trade routes, and aggregate population groups before the lobby starts with authenticated `PUT /api/games/{gameId}/economy`; the browser's **Economic scenario setup** panel uses the same API. The request requires the current `expectedWorldVersion` and the arrays `goods`, `productionRecipes`, `companies`, `markets`, and `tradeRoutes`; `populationGroups` is also sent by the current browser and is optional for older clients. Invalid configurations are rejected atomically. Each configured population need adds `dailyQuantityPerThousandPeople * group.population / 1000` to its State/good market's demand, retaining the fractional remainder between days so sub-unit needs are not lost. Actual sales are attributed proportionally to population demand, with unmet population demand recorded separately. Population-derived demand is scenario data, not official Beleland data; the model does not yet include age, occupation, wealth, wages, household money, need satisfaction, or shortage effects. There is intentionally no official Beleland price, company, demand, budget, or trade-route data seeded. Consumer budgets remain explicit per-market inputs and are not yet derived from wages. Both route forms currently omit tariffs, shipping costs, treaty authorization, exchange-rate conversion, and route disruption. State treasuries record opening balances, membership transfers, administration and construction costs, and daily balance changes; snapshots expose the most recent 100 State and company transactions. Currency IDs are tracked per State, but no currency names, codes, precision, or official monetary rules are defined. Employment, taxes, subsidies, corporate investment/insolvency, and credit remain incomplete.

Every multiplayer action now requires a client-generated order ID, the observed world version, and the selected government State. Orders persist their submission and target world dates, actor, and applicable permission set. The server derives the actor from the authenticated session, checks State membership, rejects stale versions, and records accepted and rejected results with stable machine-readable codes. Past target dates are rejected and future scheduling is explicitly unsupported until the clock can execute queued orders. Order mutations run against an isolated world copy; rejected mutations discard all partial changes, and only accepted world changes advance the public version. Economic orders are blocked unless the world is running; pause and resume votes are accepted only in the matching world state. Clock accumulator writes do not advance the public world version until a game day elapses. Each order result and its corresponding world event are saved atomically with the world; replaying an order ID returns its prior result without repeating effects. Events have a monotonic per-world sequence; authenticated snapshot recovery accepts the last received sequence and returns missed events alongside the current authoritative state. Older order records receive deterministic audit events during compatibility normalization. Authenticated `GET /api/games/{gameId}/orders` and `/api/games/{gameId}/events` endpoints read the histories. The browser persists its last event sequence and pending orders on the device, displays the pending count, and retries pending orders after reconnecting.

Economic actions check the active membership's permission set; unknown permission-set IDs fail closed. Current memberships receive the existing `government-member` permission set, and configurable roles and permission management are not available yet. Pause voting remains a game-wide vote by connected players.

The order protocol has stable typed intents for budgets, laws, appointments, treaties, mobilization, and projects. Administration, construction, pause/resume, and constitutional budget/law/office procedures have execution paths. Political procedures require an explicitly configured Constitution, institution, permission sets, and legal basis; approval rules also require an explicit quorum, threshold, and threshold denominator. Worlds do not receive invented political rules. Approved budget plans update the recorded government budget but are not yet connected to spending or accounting. Approved laws are recorded as in force with their effective world date, and office appointments affect officeholders only after any configured approval is complete. The host can configure political systems through authenticated `PUT /api/games/{gameId}/politics`; the interface for editing constitutions remains incomplete, and the other known intents are rejected until their domain rules exist.

The host can also configure provinces, settlements, explicit province connections, control records, and sovereignty history through `PUT /api/games/{gameId}/territory`; military unit types, commanders, units, routes, and supply routes through `/military`; and technology catalogs, institutions, research projects, discovery, and adoption through `/technology`. These endpoints are authenticated, host-only, lobby-only, version-checked, validated atomically, persisted in the existing JSON world record, and included in authoritative snapshots. The published Beleland map is a hand-authored SVG strategic map (geometry catalog version 2), with selectable State shapes, labelled settlements, roads, rivers, forest and mountain layers. Configured provinces can be selected by their catalogued SVG element IDs. Military units can move along configured routes, with route access, capacity, per-segment timing, and configured daily supply consumption enforced by the server. Occupations can establish or lose effective military control using scenario-configured durations and force/resistance comparisons; these events never change sovereignty. An authorized government member can start, resume, or cancel configured research projects. Starting reserves the explicitly configured budget, consumes required reserved materials, and advances each day by the configured progress amount. Completion records discovery separately from adoption and returns unused budget; cancellation returns unspent budget. Discovered technology can be explicitly adopted at State, sector, or province scope. Combat resolution and technology-effect application remain pending rather than relying on invented formulas.

Territorial scenarios validate each province's SVG mapping against the versioned external geometry catalog in `Server/Data/beleland-map-geometry.json`. The catalog records the original SVG SHA-256 and visible path/group IDs; a test compares it with `docs/Apps/NewWorld/map.svg` without modifying that asset. Each world stores its map geometry version, and territorial setup rejects unknown element IDs or mismatched catalog versions.

This remains a partial implementation of the 25-block game specification. Blocks 6–8 now have persisted, validated scenario models and basic server-backed views, but their simulation and map interaction are incomplete. Government elections, executive controls, and opposition procedures are not implemented. Configurable invitation approval, demography, justice, public services, environment, industry and labor, full finance, and advanced diplomacy also remain incomplete.

World creation stores its initial validated JSON snapshot as a baseline backup in the same PostgreSQL transaction. Each successful world update then stores the immediately previous validated snapshot and its SHA-256 checksum in the same transaction as the new state. Candidate states and previous snapshots are checked for schema and cross-world references before writing. If a world cannot be loaded because validation fails, the host may use **RECOVER PREVIOUS SAVE** in the browser or authenticated `POST /api/games/{gameId}/recover`; recovery verifies the checksum and references before replacing the current state, advances the restored world version and event sequence, records a recovery event, resets active clients for resynchronization, and retains the backup. Recovery is refused when the current save is valid, when the caller is not the host, or when the backup fails validation. Recovery discards unconfirmed client-side orders and changes made after the last backup.

Run the deterministic simulation tests from the repository root:

```powershell
dotnet test .\Apps\NewWorld\Server.Tests\Server.Tests.csproj
```

## Active browser-hosted multiplayer

The published client loads `docs/Apps/NewWorld/multiplayer.js` after the MQTT browser library. The room owner is the authority for lobby membership, State assignment, world start, supported orders, snapshots, and the host-side save. Guests send commands to the host; the host validates them and publishes the resulting shared state.

- The host must keep the original browser tab and device available while the world is online.
- Host saves are stored in that browser's local storage. They are not cloud backups and cannot be restored from another device.
- The public MQTT brokers are message relays only. They are not trusted storage and should not receive confidential personal information.
- New worlds receive a playable fictional starter economy: four firms per State, four production recipes, State-specific household demand, and grain/flour/tools markets. These are balancing defaults for the Beleland scenario, not claims about real-world economic data.
- Each host world day now runs a deterministic browser simulation in this order: government balance accrual, company production, population demand, market pricing and clearing, company cash/inventory settlement, then the day event. Each cycle is staged on a copy and committed only when every subsystem succeeds; a failed cycle pauses the world without partially applying that day.
- Production checks recipe inputs, cycle duration, batch limits, and configured output storage. Markets account for domestic stock, population needs with fractional carry, affordability, price bounds and smoothing, public import routes, and fixed-quantity bilateral company contracts. Transactions, settlements, price movements, unmet demand, activity, and world events are included in host snapshots.
- The browser-hosted order engine still supports only territory administration, construction, and pause/resume voting. Constitutional procedures, military movement/combat, research progression, demography beyond configured household demand, taxes, wages, and public-service systems are not yet fully migrated. Their screens or legacy .NET rules must not be mistaken for active browser gameplay.

The old `.NET` service is not part of the live web deployment. Running its tests validates the reference implementation only; browser simulation behavior is covered by `node --test docs/Apps/NewWorld/tests/*.test.cjs`.
