01 / Project overview

Make early system state readable.

NA.Firmware explores a firmware-layer experience that communicates what the machine is doing before an operating system starts. The central design direction is a compact POST-style dashboard: clear checks, a hardware inventory, structured diagnostic output and a legible record of failures.

The goal is not to imitate a desktop application inside firmware. It is to build an interface appropriate to the constraints of the pre-OS environment, where reliability, compatibility and predictable recovery matter more than visual effects.

01 / POST

Startup diagnostics

A concise sequence of checks with explicit states, timings and useful failure messages—once the relevant routines are implemented.

02 / INVENTORY

Hardware visibility

A structured presentation of detected components and available system information, with clear separation between detected data and unavailable values.

03 / HISTORY

Diagnostic records

A direction for retaining useful results and making recurring faults easier to investigate without implying that persistent logging is already working.

DEVELOPMENT NOTICEThis page is a project profile and static interface concept. The preview does not execute POST routines, inspect the visitor’s computer, display live telemetry or represent an installable firmware image. The project is not presented as ready for installation.

02 / Design boundaries

Keep the boot path small. Put heavy tools elsewhere.

The firmware core and the maintenance environment have different jobs. The core should initialize what is necessary, expose dependable diagnostics and hand off control safely. Larger utilities, recovery assets and detailed reports can live on a disk or recovery medium rather than being packed into the motherboard’s flash chip.

This separation keeps storage requirements realistic and avoids treating a large application bundle as if it were a conventional BIOS image.

03 / Development direction

Progress measured by verified behaviour.

The next milestones focus on proving the boot flow and diagnostic behaviour before expanding the interface. Hardware access, firmware compatibility and safe recovery are release gates—not assumptions based on a successful compile.

PHASE 01
Build and validate the EFI application

Confirm build output, architecture and basic execution in a controlled UEFI environment.

IN PROGRESS
PHASE 02
Establish a dependable diagnostic flow

Separate actual detection results, unsupported checks and failures; add clear error handling.

PLANNED
PHASE 03
Validate boot and recovery behaviour

Test entry selection, Windows Boot Manager preservation and a recovery path before any internal-disk installation is considered ready.

NOT VALIDATED
PHASE 04
Expand diagnostics after validation

Add supported hardware information and history without claiming unavailable sensors or unimplemented tests.

FUTURE
SAFETY GATENA.Firmware is not a replacement for the motherboard’s vendor firmware at this stage. Do not treat this project page or its visual preview as instructions to flash a motherboard BIOS. Any boot-entry or disk-install workflow must be separately tested and must preserve the existing Windows boot files.
